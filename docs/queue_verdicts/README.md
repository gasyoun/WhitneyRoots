## Per-queue verdict taxonomy

**Queue C** (`queue_c_verdicts.json`, `queue_c_human_residue.md`):

  pass, `fix_ppp_infinitives.py`, already moved it to `infinitives`).
- `classifier-parse-artifact` — the upstream `ppp_source_validation.py` classifier's own regex
  (`\s+[A-Z]\d.\s*`, period required) failed to strip a trailing edition tag (`E1` with no
  period); once stripped, the form is a clean `-ta`/`-na` PPP, not a morphological defect.
- `infinitive-bleed-tos` (and the `-tave`/`-dhyai` variants, none triggered in this run's data

- `confirmed-in-grammar-text` — the suspect form is a literal word in `src/wg_text.txt`
  **with the root also present in the surrounding ±200-char window, excluding the matched

  doesn't know about ordinary sandhi outcomes (-dha, -gdha, -bdha, -gna, ...).
- `residue-human` — no confident pattern; needs the Grammar §-lookup + Zalizniak per
  `REVIEWER_GUIDE.md`'s Queue C algorithm.

**Queue D** (`queue_d_verdicts.json`, `queue_d_human_residue.md`):
- `contamination-clear` — root is ≤2 chars and its section_count (≥20) is only plausible as

- `confirmed-exception` — an exception-typed section's snippet contains the bare root as a
  clean token; for ≤2-char roots this requires **two independent** exception-typed sections to
  token-match (a single hit on a 1-2 letter root is not enough evidence — see below).
- `residue-human` — ambiguous: sections exist but no clean/sufficient root-token match.

**Queue E** (`queue_e_verdicts.json`, `queue_e_human_residue.md`):

- `short-root-screening-unreliable` — root is <3 chars; a bare-prefix scan that short is too

- `citable-source-candidate` — ≥1 accented headword shares the bare-root prefix. **This is a

  the human").

## Methodology notes — false positives found and fixed during this pass

1. **`ascii_fold()` NFD-then-translate ordering bug.** An early version normalized to NFD
   *before* looking up precomposed IAST letters (ṛ, ś, ç, ...) in the fold table, so the
   fold silently never fired (NFD had already decomposed them) and leftover combining marks
   (dot-below, macron, etc.) were never stripped. Those invisible combining characters then
   satisfied a `[a-zA-Z]` word-boundary regex, producing a false match of root "kaṣ" bridging
   across `sudṛ́çīkasaṁdṛk` (an unrelated compound). Fixed by folding on the *composed* string
   first (`translate()` doesn't care about composition), then stripping any residual
   Unicode-category-Mn marks.
2. **Root-corroboration self-containment.** After fixing (1), a `confirmed-in-grammar-text`
   corroboration check ("does the bare root also appear nearby?") could be satisfied by the
   root being a literal prefix of the suspect word itself (root `kaṣ` → folded `kas` is a
   substring of its own flagged form `kasam`) — trivially "corroborating" with no independent
   evidence. Fixed by blanking the matched span out of the corroboration window before
   searching for the root.
3. **Short-root single-token-match over-confidence (Queue D).** The same class of risk as (1)
   applies to `root_token_in_snippet()` for 1-2 char roots: one token-match in ~800KB of prose
   is not strong evidence. Tightened to require 2 independent exception-typed section matches
   for roots ≤2 chars (this alone moved Queue D's confirmed count from 84 → 56 and residue from
   11 → 39 rows — the more conservative, more honest number).
